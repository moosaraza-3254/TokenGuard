## 1. Purpose and scope

TokenGuard analyzes JWTs for common configuration and implementation weaknesses, following RFC 7519 [1], RFC 7515 [2], the JWT Best Current Practices in RFC 8725 [3] and OWASP guidance [4, 5]. This document describes the weaknesses it detects, how it was evaluated, how it performed, and where it falls short.

## 2. Weaknesses detected

| Rule id | Weakness | Why it matters | Severity |
|---|---|---|---|
| `ALG_NONE` | Token declares `alg: none` (no signature) | Anyone can forge a token; a server that accepts it has no authentication. | Critical |
| `WEAK_SECRET` | HMAC secret is in a list of common secrets | An attacker can guess the secret offline and forge tokens. | Critical |
| `ALG_CONFUSION` | HS256 token signed using a public key as the HMAC secret | A public key is not secret; if a server lets the token pick HMAC, attackers can sign with the public key. | Critical |
| `HEADER_JKU` | `jku` header points to a remote key set | An attacker-controlled URL can supply the verification key. | High |
| `HEADER_KID` | `kid` header with path-like value | Can lead to path traversal or injection in key lookup. | High |
| `EXPIRED` | `exp` is in the past | Token should be rejected. | Medium |
| `NO_EXP` | No `exp` claim | Token never expires, so a leak is permanent. | Medium |
| `LONG_LIFETIME` | Lifetime far beyond a sensible window | Extends the damage window of a leaked token. | Low |
| `NBF_FUTURE`, `IAT_FUTURE`, `EXP_BEFORE_IAT` | Inconsistent time claims | Indicates a faulty or tampered issuer. | Low to Medium |
| `MISSING_ISS`, `MISSING_AUD` | No issuer or audience | Token could be replayed against a different service. | Low |
| `SENSITIVE_DATA` | Email, phone or password in payload | JWT payloads are only encoded, not encrypted; anyone holding the token can read them. | Medium |

## 3. Scoring model

Each finding adds points by severity: Critical 40, High 25, Medium 10, Low 3, Info 0. The total is capped at 100. Any Critical finding raises the score to at least 80.

| Score | Level |
|---|---|
| 0-19 | Low |
| 20-49 | Medium |
| 50-79 | High |
| 80-100 | Critical |

### Issue found during evaluation

While running the evaluation, the unsigned token and weak-secret token, the two worst weaknesses, scored only 40 and were rated Medium. The scoring simply added points, so one very serious finding could still land in a mild band. The fix was to treat any Critical finding as disqualifying: the score is raised to at least 80. Two unit tests were added (one confirming the floor, one confirming it does not apply without a Critical finding), and the report text was updated to state the rule.

## 4. Evaluation method

As planned in the proposal ("testing with controlled JWT samples"), we built 11 controlled sample tokens: 10 weak tokens, each weak in exactly one way (the key-injection and time-claim samples each trigger several related rules), and 1 well-configured control token. Every sample declares the rule ids it should trigger. `npm run evaluate` signs each sample, runs it through the same decode, weak-secret check and analyzer the app uses, and compares expected and found rule ids.

Two checks were applied:
- **Detection:** every expected rule id appears in the findings.
- **False positives:** the control token produces no findings.

Tokens were signed with Node's `crypto` for the automated run. The app signs with jsrsasign in the browser, so the samples were also loaded through the dropdown to confirm both signers produce tokens the same checks accept.

## 6. Performance

TokenGuard analyzes a token in a single pass over a few small JSON objects, so analysis is effectively instant. The only costly step is the weak-secret check, which tries each secret in a fixed list; the list is short, so this is still fast. Everything runs locally with no network calls.



## 7. Limitations

**Scope (from proposal section 3.7).** TokenGuard focuses on JWT-related security assessment rather than comprehensive web application penetration testing. It does not perform unauthorized attacks against external systems and does not provide complete security certification for applications. Its assessments are limited to supported JWT formats, available verification information, and predefined security analysis rules.

Further limitations found during development and evaluation:

1. **Self-authored evaluation.** We wrote both the samples and the rules, so 10 of 10 shows the rules work as designed. It does not show they catch every real-world weakness, and it says nothing about weaknesses we did not think of.
2. **HMAC only.** Signature verification covers HS256, HS384 and HS512. RSA and ECDSA signatures are not verified.
3. **Fixed secret list.** `WEAK_SECRET` only finds secrets in the list; a weak secret outside it will not be flagged.
4. **Static analysis.** TokenGuard examines a token you give it. It does not test whether a real server accepts forged or modified tokens.
5. **Heuristic checks.** Sensitive-data and `kid` checks are pattern-based, so they can miss unusual formats or flag harmless values.
6. **No revocation or context.** It cannot know whether a token has been revoked or whether its claims are right for your application.
7. **Small sample set.** 11 tokens is enough to demonstrate each rule, not to estimate real-world accuracy.

## 8. Lessons learned

- Testing against the real output exposed a scoring flaw that unit tests on individual rules had not: severity should influence the rating, not just add to a total.
- Keeping core logic free of DOM and crypto imports made it testable and let one pipeline serve the app, the tests and the evaluation.
- Controlled samples with one flaw each make failures easy to diagnose, and a clean control sample is essential for catching false positives.
- Checking that the browser signer and Node signer agree avoided a mismatch between what was tested and what ships.
- JWT payloads are readable by anyone holding the token, so secrets and personal data should never go in them.

## 9. Possible future work

Verify RSA/ECDSA signatures, support larger or user-supplied secret lists, add more rules (for example `typ` and algorithm allow-list checks), and evaluate against tokens from real open-source projects.
